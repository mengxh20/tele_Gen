# 方案质量检查

## 默认评价维度
- 码率效率是否更好。
- 恢复误差是否更低。
- 细节恢复和清晰度是否更稳。
- 时序连续性是否更好。
- 训练是否更稳定。
- 链路是否更贴近真实的压缩、传输与接收端恢复。

## 快速评级
- `A`
  直接服务压缩恢复主线；收益能映射到码率、恢复质量或时序一致性；改动边界清晰；尽量不动 `helios/`。
- `B`
  方向基本正确，但量化收益、链路真实性或改动边界说明还不够完整。
- `C`
  更像通用生成优化，只能间接推测对压缩恢复有帮助，缺少主链路证据。
- `D`
  明显偏离主线，或需要较大范围改写 `helios/` 却没有充分理由。

## 方案自检清单
- 这项改动是否直接作用于 `clean latents -> low_latents -> recover_latents -> metrics` 这条链路？
- 它改善的是码率效率、恢复质量、时序一致性、训练稳定性，还是链路真实性？
- 收益会体现在什么产物上：`low_latents`、`recover_latents`、`metrics` 还是仅限视频展示？
- 是否能在 `reconstruct/` 内完成？如果不能，为什么必须修改 `helios/`？
- 会不会让系统更偏向“通用生成更好看”，但对压缩恢复主线帮助不明确？

## 常见红线
- 只强调生成效果更强，却没有说明对压缩恢复的直接收益。
- 直接把视频导出效果当作主目标，忽略 latent 产物与指标。
- 为了实现需求大范围改写 `helios/`，但没有说明为什么 `reconstruct/` 不能承接。
- 把实验参数、临时脚本路径或一次性结论写进长期文档。
