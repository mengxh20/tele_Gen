# 改动边界与协作规则

## 默认改动落点
- 新增压缩恢复逻辑默认优先放在 `reconstruct/`。
- 优先通过封装、调用、适配、组合 Helios 现有能力完成需求，而不是直接改写 `helios/`。
- 默认先做最小必要修改，避免与压缩恢复主线无关的重构。

## 何时允许修改 `helios/`
- 只有在以下条件同时满足时才考虑修改：
- `reconstruct/` 中无法通过外部封装或适配完成需求。
- 修改会直接帮助低码率压缩、恢复质量、时序一致性、训练稳定性或链路真实性。
- 已说明为什么替代方案不可行。
- 已说明影响哪些模块、影响范围有多大。

## 必须先对齐的情况
- 需求存在多条实现路径，且代价或风险不明显时。
- 判断是否必须改 `helios/` 仍然不确定时。
- 当前实现已经偏离压缩恢复主线，而继续修改会扩大偏差时。

## 协作输出要求
- 每次接到需求时，先解释方案，再改代码或文档。
- 如果只是提出方案而没有改文件，要明确写出“当前仅给出方案，尚未落盘修改”。
- 完成改动后，输出中应说明：
- 影响文件
- 为什么改
- 改了什么
- 对压缩恢复主链路有什么帮助
- 如何回滚

## 文档维护要求
- 长期稳定的项目理解优先写进 `docs/`，根 `AGENTS.md` 只保留入口摘要。
- 局部目录若持续存在协作成本，可以补充局部 `AGENTS.md`。
- `AGENTS.md` 和 `docs/` 不记录一次性实验路径、临时 checkpoint、训练轮次、loss 权重等短期细节。
